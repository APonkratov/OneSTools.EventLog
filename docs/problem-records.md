# Проблемные записи ЖР

Если завершённая запись LGP или LGF не разбирается, сервис сохраняет её исходное
содержимое в обычный лог и продолжает чтение. Отдельного флага в appsettings нет.
Штатные одиночный сервис и Manager подключают файловый логгер: `log.txt` в
каталоге ContentRoot приложения. Запись также получают другие настроенные
провайдеры `ILogger<EventLogExporter>`, например консоль.

## Содержимое лога

Каждая проблемная запись получает отдельное сообщение уровня **Error**:

```text
Problem journal record in <LogFolder>/<FileName> at bytes [Position, EndPosition); stage <Stage>; <ErrorType>: <Reason>; skipped <Skipped>; encoding <Encoding>; raw <RawRecordJson>
```

- Каталог источника и имя файла позволяют различать журналы разных баз Manager.
- Position — байт открывающей скобки; EndPosition — байт после закрывающей скобки
  или конец доступного незавершённого хвоста. Диапазон полуоткрытый, с нуля.
- Stage показывает место сбоя: LGP record, dictionary entry, dictionary context,
  transaction index, event date fallback или незавершённый архивный блок.
- Тип исключения и его причина включены прямо в текст: существующий файловый
  логгер не выводит переданный объект Exception отдельно.
- При Encoding=utf-8 поле RawRecordJson содержит JSON-строку с исходным текстом,
  включая исходные пробелы, удвоенные кавычки и переносы. Переносы экранированы.
  Декодирование JSON-строки и кодирование UTF-8 восстанавливают исходные байты.
- Если байты не являются корректным UTF-8, Encoding=base64, а JSON-строка содержит
  Base64 оригинальных байтов. Подмена ошибочных байтов символом замены исключена.
- Skipped=true означает пропуск после успешного возврата обработчика логирования.
  False означает диагностическое сообщение без пропуска.

Сообщения с исходными проблемными записями не подавляются по коду события.
Обычные диагностические уведомления UnknownEvent/UnknownDataFormat и другие
по-прежнему выводят только метаданные и используют прежнее ограничение повторов.
Неизвестный, но корректный код события или резервное дерево Data не являются
поводом выбросить событие.

## Продолжение чтения

Пропускается только текущий сбалансированный корневой блок. Повторное сканирование
байтов учитывает вложенные скобки, строки и удвоенные кавычки. Поиск следующей
открывающей скобки не используется: она может находиться внутри Data или комментария.
Так обрабатываются неправильная структура/значения, ошибочный UTF-8 и превышение
ограничения глубины. Повторный скан и копирование исходного содержимого выполняются
только при ошибке. Очереди проблемных записей и буфера транзакций нет; временная
память зависит от размера одной записи или повреждённого хвоста.

Неполный хвост текущего live-файла без иной ошибки ждёт дописывания и не попадает
в лог проблемных записей. При строгом чтении незавершённого архивного LGP/LGF
содержимое хвоста записывается с Skipped=false, затем сохраняется прежняя ошибка.
Если кавычки/скобки повреждены настолько, что граница записи потеряна, безопасное
продолжение не обещается: диагностируемый остаток сохраняется, курсор не проходит
за него. Ошибки файлового ввода-вывода также не превращаются в пропуск события.

UseStrictParsing остаётся необязательной проверкой. При выключенном флаге
исторический результат DateTime.MinValue для неверной даты сохраняется, но
исходная запись дополнительно логируется с Skipped=false. При включённом флаге
завершённая запись с неверной датой или отсутствующей ссылкой LGF логируется и
пропускается. Известные формы и резервные представления корректных Data не меняются.

Разные независимые сканеры LGF и опциональный индекс исходов транзакций могут
диагностировать одну запись несколько раз. Восстановление справочника при запуске
тоже может повторно сообщить о повреждённой записи LGF. Это не повторная отправка
события в ClickHouse.

## Курсор и совместимость

Проблемная запись не получает Id и не создаёт строку-заглушку в ClickHouse.
Успешные события сохраняют прежние 24 поля, типы, порядок колонок и DDL.
EventLogItem, EventLogPosition и JSON checkpoint не меняются. Production runtime
и зависимости сохранены.

С CheckpointFile экспортёр подтверждает позицию после пропущенных LGP только
после успешной записи всего предшествующего пакета. Это работает и для
проблемного хвоста, и для источника, содержащего только проблемные записи.
Повторный запуск с сохранённым checkpoint не логирует и не читает их снова
основным потоком. Дополнительные сканеры могут перечитать их, как описано выше.
Ошибка INSERT или сохранения checkpoint не подтверждает позднейшую позицию.
Неоднозначный результат INSERT по-прежнему допускает повтор валидных событий.

Без локального checkpoint база хранит только позицию последнего успешного
события. Проблемный хвост после него может снова логироваться при запуске.
Новых колонок или таблиц ради позиции пропущенного хвоста не создаётся.

Если Error отключён и отдельного обработчика нет либо логгер/обработчик бросает
исключение, экспорт останавливается, оставляя проблемную запись непрочитанной.
Корректный предыдущий пакет можно подтвердить. Для нестандартных провайдеров
успешный вызов ILogger означает принятие сообщения провайдером, а не гарантию
физического сохранения при потере питания. Файловый логгер проекта синхронно
дописывает файл; журнал диагностики не является очередью повторной отправки.

Программные пользователи библиотеки включают поведение явно:

```csharp
settings.ProblemRecordHandler = problem => SaveProblemRecord(problem);
```

Обработчик синхронный. Без него библиотека сохраняет прежние исключения и возврат
курсора к ошибочной записи. EventLogExporterSettings также принимает такой
обработчик: он вызывается дополнительно к ILogger или используется без него.
Ошибка существующего DiagnosticHandler также прерывает чтение и не считается
повреждением записи, даже если обработчик выбросил FormatException.
Исходный текст доступен в RawRecord, формат — Encoding, безопасная строка для лога —
RawRecordJson. Сохранение и срок хранения пользовательских данных определяет
настроенный логгер; данные не отправляются разработчикам автоматически.

## Проверка 2026-10-11

- 439 тестов читателя и 88 интеграционных тестов прошли без пропусков. Среди них
  реальные запись, перезапуск и сравнение SHOW CREATE TABLE в ClickHouse
  26.8.15.10 LTS с прежними 24 колонками; проверена и запись в штатный log.txt.
- Проверены исходные байты/позиции, UTF-8/Base64, скобки в строках, глубина и
  границы буфера, ошибки обработчиков, неполные хвосты, отмена, пропущенный хвост
  после успешного/неуспешного INSERT, источник без успешных событий и повторный запуск.
- На приватном корпусе из девяти баз все поля 452 190 событий совпали с версией
  перед изменением во всех шести режимах; обработчик проблемных записей включён.
  SHA-256 всех 42 LGP и 9 LGF сохранился. Исходные журналы не публикуются.
- Контроль скорости: по три парных прогона с прогревом, переменным порядком,
  DOTNET_TieredCompilation=0 и DOTNET_gcServer=0. Медианы до/после: обычный режим
  1,650/1,620 с, пять флагов 3,232/3,215 с, контекст 4,775/4,721 с. Просадки
  на этом корпусе не обнаружено; малую разницу нельзя считать доказанным ускорением.
  Это проверка корректного потока, а не скорости записи большого числа ошибок в лог.
