# Надёжность доставки ЖР

Изменения относятся к C#-экспортеру. Go и схема ClickHouse не меняются.
События передаются по мере чтения, без ожидания будущего Commit/Rollback и без
буфера незавершённых транзакций. Существующий опциональный
`UseFinalTransactionStatuses` использует только доступные записи ЖР, как прежде.

Завершённые проблемные записи теперь можно [сохранять в лог и пропускать](problem-records.md).
Позиция после них подтверждается вместе с успешной отправкой предыдущих событий;
структура checkpoint и таблицы ClickHouse остаётся прежней.
Файловый лог теперь ротируется; при отключённом checkpoint выводится Warning.
Изменённые defaults разбора описаны в [правилах обновления](defaults-and-upgrade.md).

## Исправленное поведение

- На один источник выполняется один INSERT. Следующий пакет не читается и не
  отправляется до подтверждения предыдущего и сохранения локального состояния,
  если оно включено. Ошибка останавливает попытку экспорта; сервис повторяет её.
- Память очереди ограничена одним пакетом `Portion` на источник. Это число событий,
  а не лимит байтов: размер Data, буферы драйвера и справочники читателя также
  занимают память. Нового буфера транзакций нет.
- Архив завершается на EOF и отправляет неполный последний пакет. Одиночный сервис
  после успеха завершает host; Manager оставляет наблюдение за кластером, но не
  запускает успешно прочитанный архив повторно до удаления/добавления базы.
- Остановка прекращает чтение и ждёт записи остатка. `ShutdownTimeout` ограничивает
  ожидание после запроса остановки, включая уже выполняющийся INSERT. После
  истечения срока неподтверждённая позиция не сохраняется. Пользовательский
  приёмник, игнорирующий отмену, может закончить запрос позднее: повторы возможны.
- Manager отслеживает настоящие async-задачи и ждёт их завершения. Повторное
  добавление базы ждёт остановки предыдущего экспортера этой базы.
- ClickHouse выбирает позицию по `FileName DESC, EndPosition DESC, Id DESC`.
  Откат часов события больше не возвращает курсор назад. Имена LGP должны быть
  штатными именами периодов. Табличный `ORDER BY (DateTime, EndPosition)` сохранён;
  запрос восстановления по файлу может требовать сканирования большой таблицы.
- Если сохранённый LGP отсутствует либо LGP/LGF короче подтверждённой позиции,
  запуск завершается ошибкой. Автоматический сброс курсора мог бы скрыть потерю
  истории. Нужны восстановление файлов или явно запланированный повторный импорт.
  Исключение совместимости при получении старой позиции из БД — историческое
  смещение на один байт за EOF: оно принимается и нормализуется к длине файла.
  Новые локальные позиции точные и такого допуска не получают.

`WritingMaxDegreeOfParallelism` / `WritingMaxDop` и `CollectedFactor` принимаются
для совместимости конфигурации, но параллельная очередь внутри одного источника
больше не используется. При степени параллелизма больше 1 выводится предупреждение.
Это сознственное изменение поведения: пропускная способность на некоторых
нагрузках может снизиться; разные базы Manager продолжают экспортироваться
параллельно. Размер пакета можно настраивать после измерений.

## Локальное подтверждение позиции

Для одиночного экспортера можно дополнить существующую секцию:

```json
{
  "Exporter": {
    "CheckpointFile": "C:/ProgramData/OneSTools/checkpoints/ib-a.json",
    "ShutdownTimeout": 30
  }
}
```

Manager вместо `CheckpointFile` принимает `CheckpointDirectory`: он создаёт
отдельное имя файла по пути источника и имени БД. Настройки необязательны и по
умолчанию пусты; `ShutdownTimeout` по умолчанию 30 секунд, допустимо 1..3600.
Встроенные host получают ещё 5 секунд на завершение. При размещении как служба
или контейнер внешний срок остановки должен позволять выполнить это ожидание.
При использовании библиотеки host и ожидание `StartAsync` перед `Dispose`
обеспечивает вызывающая сторона.

Локальное состояние хранит только подтверждённый непрерывный префикс:

1. При первом запуске сохраняется исходная позиция **до первого INSERT**.
   В live-режиме она берётся из приёмника; при `LoadArchive=true` это начало
   журнала. Пустая позиция тоже сохраняется.
2. После успешной записи всего пакета сохраняется позиция его последнего события.
3. При восстановлении локальная позиция имеет приоритет над строками приёмника,
   включая сохранённое начало журнала. В архивном режиме она позволяет продолжить
   импорт, а не перечитывать весь архив.

Это необходимо при частичном INSERT: в ClickHouse могла попасть поздняя строка
пакета, хотя его начало не записалось. Максимальная позиция таблицы тогда не
доказывает доставку предшествующих строк. Границы атомарности INSERT зависят от
блоков и партиций; потеря ответа также оставляет результат неизвестным
([официальная документация ClickHouse](https://clickhouse.com/docs/concepts/features/operations/insert/transactions)).

Состояние привязано к полному пути источника и хешу адреса приёмника/имени БД.
Пароли в нём не сохраняются. Для своих реализаций `IEventLogStorage` добавлен
необязательный `IEventLogStorageIdentity`: следует вернуть стабильный идентификатор
назначения без секретов. Без этого интерфейса используется имя типа, поэтому
различить два назначения одной пользовательской реализации невозможно.

Файл `.lock` удерживается открытым на время экспорта и содержит отметку
инициализации. Два процесса с одинаковым checkpoint не запускаются одновременно.
JSON записывается во временный файл в том же каталоге, сбрасывается на диск и
заменяет старую версию. Повреждённое состояние, несовпадение привязки или исчезновение
JSON при сохранённой отметке `.lock` приводят к ошибке, без отката к курсору БД.

Нужен постоянный локальный каталог с правом записи, сохраняемый при обновлении
приложения/контейнера. Не размещайте его в очищаемом временном каталоге. Храните
JSON вместе с `.lock`; удаление обоих неотличимо от первого запуска. Преднамеренный
полный импорт требует отдельного нового checkpoint и контроля повторов.

## Гарантии и границы

### Повторный запуск с 15 файлами ЖР

При включённом `CheckpointFile` после подтверждения последнего пакета и успешного
сохранения позиции обычный перезапуск не отправляет подтверждённые события снова.
Все 15 LGP могут оставаться в каталоге: экспорт продолжается с сохранённых имени
файла и смещения. Если дописан последний файл или появился следующий период,
передаются только новые события. При запуске с `LoadArchive=true` сохранённая
локальная позиция тоже учитывается.

Проверка закреплена двумя тестами: 45 событий в 15 файлах, повторный запуск с
нулём INSERT, затем live-перезапуск с добавлением по событию в последний и новый
файлы. Получено ровно 47 уникальных позиций, без повторов первых 45 событий.
Изменение mtime прочитанных файлов не вызывает повторную отправку.

Гарантия относится к экспорту событий. Читатель может открывать файлы для
восстановления справочника и, при соответствующей опции, индекса транзакций;
отсутствие любого повторного файлового чтения не обещается. Checkpoint необходимо
явно включить и сохранять вместе с `.lock` между запусками. При утраченном либо
повреждённом JSON и сохранённом `.lock` экспорт останавливается с ошибкой.

### Неизвестный исход INSERT

При сохранённом checkpoint, доступных исходных журналах и одном писателе ошибка
или неизвестный результат INSERT приводят к повтору неподтверждённого пакета.
**Дубли возможны.** Дедупликация, exactly-once, spool и новые таблицы не вводятся.
В частности, ClickHouse может записать пакет до аварии экспортера, а локальная
позиция останется прежней. Сохранение позиции перед INSERT исключило бы повтор,
но могло бы потерять события при неуспешной записи, поэтому так не делается.
Для защиты от дублей в этом окне нужен отдельный контракт идемпотентной записи
приёмника. Локальный checkpoint сам по себе такой гарантии не даёт.
Включение checkpoint впервые доверяет прежней позиции БД и не исправляет уже
существующие пропуски.

Со старой конфигурацией восстановление продолжает брать позицию из БД. Пакеты
теперь упорядочены, но при частичной записи или неизвестном результате такой
курсор по-прежнему может скрыть пропуск. Для защиты от этого сценария нужно
явно включить локальное состояние.

Блокировка защищает только один и тот же путь checkpoint на одной файловой
системе; разные пути/машины не обеспечивают распределённого запрета второго
писателя. Подмена журнала другим поколением с тем же именем и достаточной длиной
не обнаруживается. Файлы ЖР должны сохраняться до подтверждения доставки;
checkpoint не заменяет резервное копирование ЖР и ClickHouse.

Сброс файла и замена состояния не являются доказательством устойчивости к потере
питания на любой ОС/ФС: синхронизация каталога отдельно не реализована.
Надёжность дисков, настройки подтверждения и сохранности ClickHouse — отдельный
контракт. Потеря питания, сетевые разделения, авария самого сервера и заполнение
диска ClickHouse не воспроизводились. Проверены HTTP 503, реальный обрыв
TCP-ответа после INSERT, принудительное завершение отдельного процесса Core
и настоящий ENOSPC при публикации checkpoint в ограниченном тестовом tmpfs.
Есть отдельная проверка ошибки публикации checkpoint после
успешного INSERT. Подробности — в [проверке восстановления ClickHouse](clickhouse-recovery.md).

Elasticsearch остаётся доступным; отмена записи теперь выбрасывает исключение,
чтобы неполный пакет не выглядел успешным. Реальный Elasticsearch в этих тестах
не запускался. CORP проверяется отдельно после получения файлов.

## Проверки

- 89 тестов читателя и 62 теста экспортера/контракта входят в набор проверок.
  Из последних 27 проверяют доставку, 3 — жизненный цикл сервисов и 8 используют
  настоящий ClickHouse 26.8.15.10 LTS с прежним драйвером.
- Проверены ошибка записи, частично записанный первый/следующий пакет, потеря
  ответа после полной записи, отмена и зависание приёмника, остаток при остановке,
  архивный EOF, блокировка/повреждение/исчезновение checkpoint, смена назначения,
  усечение исходных файлов и ошибка checkpoint после записи пакета.
- В ClickHouse сохранены upstream DDL, порядок/типы 24 колонок и все значения.
  Новый тест действительно записывает только позднюю строку первого пакета,
  затем восстанавливает экспорт: все события присутствуют, повтор виден явно.
- На приватных копиях 42 LGP и 9 LGF из девяти файловых баз передано 452 190 событий
  за 117 пакетов. Поток экспортера совпал с прямым читателем по SHA-256 сериализации
  всех 24 свойств для каждой базы. Девять повторных запусков с checkpoint дали
  ноль событий; четыре поля позиции совпали с последним подтверждённым событием.
  SHA-256 всех 51 исходного файла копии сохранился. Это проверка доставки в
  контролируемый приёмник; полный приватный корпус в ClickHouse не загружался.

Исходные личные журналы не входят в репозиторий; публичные тесты синтетические.
Runtime, пакеты production-проектов, `EventLogItem` и `EventLogPosition` сохранены.
