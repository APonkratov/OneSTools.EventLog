# Совместимые исправления экспортера

Уточнение пользователя: улучшенный разбор теперь включён по умолчанию, лишние
флаги удалены из типовой конфигурации. Явные прежние ключи и публичные свойства
сохранены для совместимости. Схема ClickHouse остаётся прежней; изменение значений
при отсутствующих настройках описано в [правилах перехода](defaults-and-upgrade.md).

Рабочий форк: https://github.com/APonkratov/OneSTools.EventLog

Upstream: https://github.com/akpaevj/OneSTools.EventLog

Все доработки экспортера ведутся в одной ветке `codex/improve-eventlog-exporter`
и одном накопительном PR в `master` форка. Исправления разделяются тематическими
коммитами, регрессионными тестами и описанием влияния на совместимость.
Прежняя цепочка PR #1–#11 объединена с сохранением истории коммитов.
Новые тематические PR для этой работы не создаются. Перенос в upstream выполняется отдельно.

## Обязательные ограничения

- Существующая ClickHouse-таблица EventLogItems сохраняется: имена, порядок и типы 24 колонок, кодеки, MergeTree, PARTITION BY, ORDER BY и SETTINGS. Миграции, ALTER и новые обязательные таблицы не вводятся.
- Позиционный порядок 24 значений в ClickHouseBulkCopy сохраняется. Data остается String; другие поля также сохраняют свои типы.
- Не меняются имена и типы существующих публичных свойств EventLogItem, обязательные параметры конфигурации, формат сохраненной позиции FileName/EndPosition/LgfEndPosition/Id и варианты приемника.
- Совместимость схемы БД и совместимость значений — разные требования. Изменение представления события, статуса транзакции или формата Data может нарушить существующие отчеты даже при неизменной таблице. Такие изменения отделяются от исправления чтения и получают явно включаемый режим с сохранением прежнего поведения по умолчанию либо согласованный переходный контракт.
- Диагностические исходные блоки и дополнительные сведения не требуют новых колонок: до отдельного решения используются тестовые артефакты/диагностика, а не расширение EventLogItem, которое могло бы изменить сериализацию приемников.
- Смена языка, отказ от Elasticsearch и обновление целевых runtime не входят в исправления парсера. Это самостоятельные решения.

## Переход между LGP

При одинаковом mtime библиотека пропускала следующий файл; при изменении mtime после копирования нарушала порядок. Следующий файл теперь выбирается по имени периода yyyyMMddHHmmss.lgp независимо от mtime. Фильтр SkipEventsBeforeDate применяется к времени события, а не к файловым атрибутам. Пустой архив возвращает null, пустой live-журнал использует существующий ReadingTimeout.

Сохранены существующий формат позиции, значения полей, Data и Comment, представления событий и транзакций. Код ClickHouseStorage, EventLogItem, LgpReader и настройки не изменены. Новые зависимости относятся только к проекту тестов; библиотека остается netstandard2.1, экспортер — на прежнем target framework.

Проект тестов запускается отдельно от существующего solution, чтобы не повышать требования к его локальной сборке. В GitHub Actions установлен SDK 8 вместо SDK 5.0.100: прежний SDK в текущем ubuntu-latest падает до восстановления пакетов с `No usable version of libssl was found`. Это изменение инструмента CI, а не target framework или runtime поставляемого экспортера.

Тесты запускаются командой:

```shell
dotnet test OneSTools.EventLog.Tests/OneSTools.EventLog.Tests.csproj --configuration Release
```

Ограничения: порядок опирается на штатные имена LGP. Произвольно переименованные архивы требуют отдельной обработки. Для SkipEventsBeforeDate старые файлы теперь могут просматриваться до нахождения подходящих событий, что добавляет чтение большого архива, но исключает ошибочный пропуск по mtime. Файлы с периодом до сохраненного курсора автоматически не переигрываются: восстановление уже потерянной истории выполняется отдельно и требует контроля повторов.

## Блоки доработок в общей ветке

Ниже сохранено описание блоков, первоначально подготовленных отдельными PR;
теперь все они входят в общую ветку и проверяются совместно.

Контракт ClickHouse проверен на свежей LTS 26.8.15.10 (официальный `clickhouse:lts` на 2026-10-10), с существующим драйвером 3.0.0.357. Добавлен отдельный [интеграционный набор](../OneSTools.EventLog.Exporter.IntegrationTests/README.md): сравнение существующей/созданной таблицы с upstream DDL, все 24 значения, нормализация null и продолжение по сохраненной позиции. В CI версия и digest закреплены. Это проверка контракта и штатного перезапуска; устойчивость доставки к авариям и конкурентным пакетам проверяется отдельно.

1. Контракт существующих приемников: интеграционный контракт ClickHouse закреплен; для Elasticsearch требуется отдельная проверка. При изменении экспорта повторять проверки ClickHouse, не ограничиваясь сравнением исходного DDL.
2. Исправленные N/D/S, экранирование и U/C/R работают всегда. [Контракт значений](value-parsing.md).
3. Именованные сложные данные и резервное дерево работают всегда. [Контракт данных](structured-data.md). Байтовые курсоры, обновления LGF и доступные исходы транзакций также без переключателей. [Контракт курсоров](journal-checkpoints-and-outcomes.md).
4. Именованные P/Z, ссылки, каталог 123 кодов и проверки работают всегда; только контекст разделения и дополнительные поля остаются под UseEventContext. [Контракт](noncorp-parsing.md). CORP отдельно, схема ClickHouse и зависимости сохранены.
5. Подготовлено исправление надёжности: последовательное подтверждение пакетов, архивный EOF, ожидание остановки сервисов и необязательное локальное состояние для повтора неоднозначного INSERT. [Контракт, настройки, проверки и ограничения](export-delivery.md). Старая конфигурация работает; для защиты от пропусков после частичного INSERT checkpoint включается явно. БД сохраняется, возможны дубли. Go и ожидание будущего исхода транзакции не входят в изменение.

## CORP — отдельный набор

Пользователь предоставит настоящие LGF/LGP от CORP-платформы. До получения этих файлов покрытие CORP не заявляется. Для набора фиксируются точная версия платформы, формат ЖР, сценарий получения события и штатная выгрузка 1С. Оригиналы не публикуются: сначала проверяются персональные/служебные данные и пригодность минимального обезличенного примера для открытого upstream. Основные исправления не должны ждать CORP, если воспроизводятся на обычной платформе.
