# Разбор обычной платформы перед проверкой CORP

Актуальные значения по умолчанию изменены по решению пользователя:
[штатный разбор и переход](defaults-and-upgrade.md). Ниже сохранены контракты
отдельных режимов и результаты первоначальной проверки; пять улучшений теперь
включены без явных флагов, контекст и строгая проверка остаются выключенными.

Изменения расширяют разбор содержимого ЖР и диагностику, сохраняя существующие
24 поля `EventLogItem`, типы и порядок колонок ClickHouse, DDL и зависимости.
Улучшенные представления включены по умолчанию. Они применяются при следующем чтении;
уже загруженная история не переписывается.

## Настройки

Одинаковые флаги доступны в `EventLogReaderSettings`, `EventLogExporterSettings`,
разделе `Exporter` одиночного сервиса и Manager. StructuredDataParsing и
CurrentEventNames теперь по умолчанию **true**, EventContext и StrictParsing — **false**.

| Настройка | Что меняется при включении |
| --- | --- |
| `UseStructuredDataParsing` | Расширенный именованный JSON и резервное дерево в прежнем `Data String` |
| `UseCurrentEventNames` | Расширенный каталог представлений в прежнем поле `Event` |
| `UseEventContext` | Конверт контекста в `Data`: исходные коды, данные, дополнительные поля и разделители |
| `UseStrictParsing` | Ошибка вместо недостоверной даты, неразрешённой ссылки LGF или незавершённого архивного блока |

Флаги независимы. `UseCorrectedValueParsing` и `UseLatestDictionaryValues` также
сохраняют поддержку явных настроек; оба теперь включены по умолчанию.
`UseFinalTransactionStatuses` тоже включён: разбор не ожидает будущего завершения транзакции и не
добавляет буфер событий транзакции.

Например, для новых именованных данных и строгой проверки, сохраняя прежние
представления событий и прежний внешний формат `Data` без конверта контекста:

```json
{
  "Exporter": {
    "UseCorrectedValueParsing": true,
    "UseStructuredDataParsing": true,
    "UseCurrentEventNames": false,
    "UseEventContext": false,
    "UseStrictParsing": true
  }
}
```

Перед включением `UseEventContext` необходимо адаптировать запросы к `Data`.
Схема БД остаётся прежней, но формат значения этой колонки меняется. Переключение
настроек само по себе не приводит к повторному экспорту подтверждённых событий.

## Именованные данные

Дополнены следующие проверенные формы:

- `AuthenticationError`: варианты P/513 и P/518, с разным составом полей.
- `ExclusiveModeChangeError`, `AccessDenied`, `ConfigExtensionApplyError`.
- `ExternalDataProcessorConnect` и `ExternalReportConnect`: шесть полей,
  включая путь, имя, безопасный режим и защиту от опасных действий.
- Обновление расширения, обновление/ошибка обновления расширения БД и удаление
  расширения БД: пятнадцать полей, включая Purpose, Scope, DefaultRoles и флаги.
- Таблицы Z для доступа и изменения/инициализации предопределённых данных:
  несколько строк и колонок, пустая таблица, строковые ячейки. Проверяются
  количество, описатели и уникальность имён. Неизвестный описатель, иной тип
  ячейки или нарушенная форма сохраняются целиком резервным деревом.

Именованные формы с фиксированными полями сверены со штатным JSON `ibcmd`
8.3.27.2325. Числа и логические значения представлены строками, как в этой
выгрузке. Для таблиц сохранены её правила одиночного объекта/массива: одна
колонка или строка — объект, несколько — массив; при нуле строк поля Row нет.

Самоописывающиеся P-блоки `{количество,{имя,значение},...}` получают отдельный
контракт, независимо от кода события:

```json
{
  "$format": "1c-named-data-v1",
  "values": {
    "ИмяПредопределенныхДанных": "FixtureName",
    "Ссылка": {"$type":"@","value":"255:11111111111111111111111111111111"}
  },
  "nodes": ["P", ["2", ["ИмяПредопределенныхДанных", ["S", "FixtureName"]], ["Ссылка", ["@", "255:11111111111111111111111111111111"]]]]
}
```

Здесь S/N/B/D декодируются, U сохраняется как `{"$type":"U"}`, @/R — как
типизированная идентичность ссылки. Штатный экспорт может выдавать для ссылки
null либо представление «Объект не найден». Библиотека сохраняет саму ссылку и
не утверждает наличие объекта. Поэтому такой конверт намеренно не равен
штатному JSON побуквенно. `nodes` сохраняет всё исходное дерево; неизвестный
тип значения, повторяющееся имя или неверное количество дают резервный
`1c-brackets-v1` для **всего** блока.

Маскированные позиционные P-блоки пользователей, параметров базы и парольной
политики получают `1c-positional-data-v1`: `layout`, подтверждённые `values`,
список `unnamedFields` и полное дерево `nodes`. Их поля проверены раздельным
изменением свойств в изолированной базе **8.3.27.2325**. Штатный `ibcmd` отдаёт
для этих блоков `Data=null`, поэтому ожидания взяты из выполненных операций,
а не из штатного JSON. Эти блоки встречаются и в свежем ЖР, слово «старые» не
описывает их область применения. Подробный контракт, позиции и границы:
[позиционные данные](positional-data.md).

## Контекст и разделители

При `UseEventContext=true` содержимое `Data` имеет формат:

```json
{
  "$format": "1c-event-context-v1",
  "EventCode": "_$Data$_.NewPredefinedData",
  "ApplicationCode": "1CV8C",
  "Data": "прежнее выбранное представление Data, включая JSON как строку",
  "DataNodes": ["S", "пример"],
  "ExtraFields": ["0", ["1", "1", "1"]],
  "SessionDataSeparation": {"Tenant":"123"},
  "SeparationDictionary": [
    ["9", "11111111-1111-1111-1111-111111111111", "Tenant", "1"],
    ["10", ["N", "123"], "1", "1"]
  ]
}
```

Пример показывает форму конверта, а не полную запись одного события.
`ExtraFields[0]` соответствует полю LGP с индексом 17, `[1]` — индексу 18 и
так далее. Сохраняются все дополнительные поля, включая неизвестные.
`DataNodes` и `ExtraFields` — разобранное дерево, не побайтовая копия файла:
внешние кавычки и форматирующие пробелы между узлами не сохраняются, удвоенные
кавычки внутри листьев сохраняются.

LGF/9 задаёт имя/UUID разделителя, LGF/10 — типизированное значение.
Поддержаны S/N/B/D и несколько разделителей. Неразрешённый или неизвестный
вариант даёт `SessionDataSeparation=null`, диагностическое уведомление и
сохранённые исходные дополнительные поля с доступными записями справочника.
Значения разрешаются по последним завершённым записям отдельного справочника;
это не реконструкция имени разделителя на исторический момент события.
Этот справочник не изменяет прежнее ленивое разрешение основных полей LGF.

Неизвестные записи LGF, включая 11/12/13, доступны целиком в `NodesJson`
программного обработчика диагностики. Они не объявляются семантически
расшифрованными и не копируются все вместе в каждое событие.

Примеры запросов к прежней колонке String:

```sql
SELECT JSONExtractString(Data, 'SessionDataSeparation', 'Tenant') FROM EventLogItems;
SELECT JSONExtractString(JSONExtractString(Data, 'Data'), 'values', 'Ссылка', 'value') FROM EventLogItems;
```

Память расходуется на справочники LGF и текущую запись; буфера открытых
транзакций нет. Конверт увеличивает объём Data: он содержит исходное дерево
вместе с выбранным представлением, поэтому включается отдельно.

## Каталог событий

Вместе с сохранённой исторической картой покрыты все **123 кода** из модели
`ibcmd eventlog model export` 8.3.27.2325. Каталог дополняет прежнюю карту;
пользовательские и будущие неизвестные коды сохраняются как есть.
[CSV](event-catalog.csv) содержит 98 добавленных/уточнённых представлений:
39 подтверждены штатным экспортом, 59 являются переводами документированных
кодов. Переводы не выдаются за проверенные дословные подписи платформы.
Имена из более новой справки подтверждают только наличие записей каталога,
а не покрытие их содержимого или CORP.

## Ошибки и диагностика

`DiagnosticHandler: Action<EventLogDiagnostic>` доступен программным клиентам.
Уведомление содержит Code, FileName, Position, EventCode и, для части случаев,
NodesJson. Последний может содержать пользовательские данные; их хранение
определяет вызывающий код. Обработчик синхронный: его исключение прерывает чтение.
LGF может диагностироваться обоими независимыми читателями; обработчик должен
допускать повторные уведомления.

Для этих уведомлений сервис пишет только метаданные, без NodesJson. Повторы по
Code/EventCode подавляются, максимум 1000 разных ключей за запуск.
Коды включают UnknownEvent, UnknownDataFormat, DictionaryRecord,
UnresolvedSeparation, ExtraLgpFields, InvalidRecord, InvalidDate,
InvalidDictionary и IncompleteRecord.

Отдельный обработчик `ProblemRecordHandler` позволяет записать исходную
проблемную запись и продолжить чтение. Сервис автоматически направляет такие
записи в свой `log.txt` с уровнем Error. Для них подавления повторов нет.
Подробности, условия пропуска и сохранения позиции:
[логирование проблемных записей](problem-records.md).

Без этого обработчика ошибочная завершённая запись приводит к `EventLogParseException` с именем
файла и байтовой позицией. Курсор возвращается к началу записи, Id не
увеличивается. После исправления файла можно повторить чтение. Строгий режим
дополнительно отвергает неверную дату и отсутствующие ссылки основных полей.
Он не запрещает неизвестные данные, сохранённые резервным деревом, и не является
полной проверкой недокументированного файлового протокола/заголовков.

В строгом архивном режиме незавершённый LGP/LGF вызывает ошибку. В live-режиме
читатель ждёт дописывания; появление следующего LGP не разрешает молча пропустить
незавершённый предыдущий файл. Подтверждённый корректный префикс экспортируется
и сохраняется в checkpoint до сообщения об ошибке следующей записи.

Невалидный UTF-8 и глубина более 256 блоков отвергаются во всех режимах.
Итеративный разбор устраняет StackOverflow зависимости BracketsFile 2.1.9 при
пробелах/переносах после закрывающей кавычки, сохраняя её публичную модель узлов.
Также устранён сбой запоздавшего callback FileSystemWatcher после Dispose.

## Проверка и границы

- Девять локальных снимков: **452 190 событий, 42 LGP и 9 LGF**. Все прочитаны
  с новыми режимами, включая строгий; значения при выключенных флагах совпали
  с сохранённым исходным reader, кроме ранее исправленных байтовых позиций.
- **15 650** сложных записей получили именованные данные: 9079 с фиксированной
  формой штатного экспорта, 6521 самоописывающихся и 50 позиционных.
  До расширения их было 1787. У пользователей именованы 19 подтверждённых полей;
  остальные позиции сохранены без предполагаемых имён.
- Из прежних **156 записей** 42 относятся к созданию/изменению пользователей и
  их ошибкам, семь — к параметрам базы, одна — к новой парольной политике.
  Остальные **106** содержат пустой P: 68 `DBConfigUpdate` и 38
  `DBConfigExtensionUpdate`. Для них остаётся резервное дерево без выдуманного
  содержимого. Это число записей, а не число разных форматов.
- Контекст **432 796** событий совпал со штатным SessionDataSeparation.
  В этих журналах разделители нулевые; ненулевые N/S/D проверены отдельно.
- Восстановление с новыми режимами проверено в 60 точках, включая переходы
  между файлами. Сравнивается следующее событие и содержимое контекста;
  исторические особенности значения LgfEndPosition проверялись отдельно.
- Открытые fixtures: 86 искусственных сложных Data для 18 кодов, четыре
  разделителя и четыре формы именованных ссылок. Ожидаемый результат экспортирован
  реальным ibcmd 8.3.27.2325; оригинальные журналы не публикуются.
- Ещё 78 искусственных позиционных записей: текущая форма пользователей
  P/65535, историческая форма P/65534, парольная политика P/255 и шесть масок
  параметров. Все 78 приняты штатным ibcmd 8.3.27.2325, все дали `Data=null`.
  Имена/значения проверяются по контролируемым операциям; историческая форма
  адаптирована с сохранением наблюдённого порядка и без оригинальных данных.
- Reader-тесты и интеграционные тесты проверяют независимость настроек,
  malformed/unknown, UTF-8, глубину, дописывание, курсор, Manager и оба конструктора
  экспортёра. На ClickHouse **26.8.15.10 LTS** проверены запись/SQL-запросы новых
  конвертов, все 24 колонки и неизменность SHOW CREATE TABLE.

Итог локального запуска: **390 reader-тестов и 74 интеграционных теста**, без
пропусков; production solution собран. SHA-256 всех 51 исходного файла снимков
остался прежним. В открытом PR публикуются только искусственные fixtures,
каталог и агрегированные результаты, без исходных журналов и частных отчётов.

Исторические файлы могли быть записаны более ранними версиями 1С; 8.3.27.2325 —
версия независимого экспортёра для сверки. Покрытие каталога не означает
семантическое покрытие всех вариантов Data всех 123 событий или всех версий 8.3.27+.
CORP ждёт отдельного корпуса. Go, Managed ClickHouse и защита от дублей после
неоднозначного INSERT остаются отдельными задачами.
