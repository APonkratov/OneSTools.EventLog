# Скорость чтения ЖР: форк и апстрим

Последующая оптимизация измерена в [отдельном отчёте](performance-optimization-2026-10-11.md).
Ниже сохранены исходные замеры до неё.

Измерены апстрим `c95a2bf` (актуальный upstream/master после fetch) и код reader
форка `e574880`. Production-код во время замеров не менялся.

На этом корпусе режим по умолчанию ускорился **в 2,39 раза**, а исправленный
и структурированный разбор Data — **в 2,25 раза относительно апстрима**.
Стоимость JSON-разбора относительно нашего default составила **6% времени**.
Включение сразу всех дополнительных проверок и полного контекста заметно дороже;
эти режимы измерены отдельно и не включаются автоматически.

## Условия

- Одни и те же девять неизменяемых снимков: **452 190 событий**, 42 LGP,
  девять LGF, **83 951 154 байта / 80,06 MiB**.
- Windows 11 Pro 10.0.26300, AMD Ryzen 7 7735HS, 8 ядер / 16 потоков,
  план питания Balanced. Другие локальные приложения не останавливались.
- Release, **.NET 8.0.31 x64**, workstation GC. Основная серия с
  `DOTNET_TieredCompilation=0` и `DOTNET_gcServer=0`, одинаково для двух версий.
  Это стенд сравнения библиотек, не замер production-службы под .NET 5.
- Часовой пояс Europe/Moscow, `LiveMode=false`, чтение с начала архива.
  `UseFinalTransactionStatuses=false`: индекса/ожидания исходов транзакций нет.
- Перед каждым измерением — полный прогревочный проход в отдельном процессе.
  Семь измерений основных режимов с чередованием версий; приведена медиана.
  Кэш файловой системы прогрет; скорость холодного диска/сетевой папки не измерялась.
- Компиляция, запуск процесса и прогрев исключены из таймера. Время создания и
  освобождения reader и разрешения словарей включено. Результаты потребляются
  прямым вызовом API, без reflection/JSON-сериализации EventLogItem в цикле.

## Reader без ClickHouse

| Режим | Прогонов | Время всего корпуса, с | Событий/с | Диапазон времени, с |
| --- | ---: | ---: | ---: | ---: |
| Апстрим, default | 7 | 4,695 | 96 320 | 4,638–4,866 |
| Форк, default | 7 | 1,965 | 230 101 | 1,943–1,982 |
| Форк, исправленный + структурированный Data | 7 | 2,083 | 217 063 | 2,028–2,252 |
| Форк, только актуализация LGF | 3 | 3,792 | 119 256 | 3,670–3,808 |
| Форк, только строгий режим | 3 | 3,801 | 118 962 | 3,702–3,860 |
| Форк, все пять дополнительных флагов без контекста | 7 | 5,487 | 82 414 | 5,423–5,598 |
| Форк, те же флаги + полный контекст | 7 | 7,035 | 64 275 | 6,900–7,232 |

Точные наборы флагов:

- `data`: UseCorrectedValueParsing + UseStructuredDataParsing.
- `latest`: только UseLatestDictionaryValues.
- `strict`: только UseStrictParsing.
- «Все пять»: UseCorrectedValueParsing, UseStructuredDataParsing,
  UseCurrentEventNames, UseLatestDictionaryValues, UseStrictParsing.
- «Контекст»: все пять + UseEventContext.

Все основные режимы вернули ровно 452 190 событий. У двух default-версий
совпали сумма длин Data и лёгкая агрегатная контрольная сумма. Это дополнительная
проверка согласованности; полное сравнение полей с апстримом ранее выполнено
отдельным валидатором, не влияющим на бенчмарк.

Дополнительно выполнены по два контрольных измерения default/data с обычной
tiered compilation после двух прогревов. Преимущество форка сохранилось.
Эта малая серия не подменяет семь основных измерений и не используется для
точного заявления о производительности production-runtime.

## Память и размер Data

| Режим | Выделено управляемой памяти, байт/событие | Медиана пикового working set процесса, MiB |
| --- | ---: | ---: |
| Апстрим, default | 6 024 | 45,9 |
| Форк, default | 5 951 | 70,2 |
| Форк, data | 6 103 | 67,6 |
| Форк, все пять флагов | 6 468 | 66,5 |
| Форк, контекст | 12 367 | 67,6 |

Выделенные байты — суммарные аллокации, не размер удерживаемой кучи.
Working set включает прогрев, JIT и нативную память. Ускорение default
сопровождается большим пиком процесса: примерно **+24 MiB** на этом стенде.
По одному размеру корпуса нельзя выводить асимптотику памяти.

Сумма `Data.Length` равна 4 251 286 в default, 9 650 047 при всех пяти флагах
и 243 711 396 с контекстом. Это длина строк .NET, **не** число UTF-8 байт,
не размер HTTP-трафика и не объём сжатых данных ClickHouse. Контекст сохраняет
код события, исходное дерево, дополнительные поля и разделители рядом с
выбранным Data, поэтому значительно увеличивает логический объём этой колонки.

## Чтение и запись в ClickHouse

Отдельный Docker ClickHouse **26.8.15.10 LTS**, образ закреплён по digest.
Пакеты 10 000, одна последовательная запись, одинаковый ClickHouse.Client и
собственный ClickHouseStorage каждой версии. Все снимки записываются в новую
временную таблицу с существующей схемой; перед каждым измерением — полный
прогрев с отдельной БД. По три измерения с чередованием версий.

Подключение и создание таблицы исключены из времени. Чтение, выделение пакетов,
сериализация, HTTP-вставка и ожидание подтверждения INSERT включены.
После каждого прохода проверены число сохранённых строк, 24 колонки и
неизменность SHOW CREATE TABLE; тестовая БД удалена.

| Режим | Время всего корпуса, с | Событий/с | Диапазон времени, с |
| --- | ---: | ---: | ---: |
| Апстрим, default | 11,738 | 38 524 | 11,540–11,787 |
| Форк, default | 9,498 | 47 611 | 9,363–9,525 |
| Форк, data | 9,631 | 46 954 | 9,489–9,644 |
| Форк, все пять флагов + контекст | 14,164 | 31 926 | 14,136–14,351 |

По пропускной способности default форка выше апстрима на **23,6%**, режим
data — на **21,9%**. Полный контекст увеличил время относительно апстрима
на **20,7%**, относительно нашего default — на **49,1%**.
Во всех измерениях сохранено ровно 452 190 строк; схема не менялась.
Тестовый контейнер после завершения удалён.

Это сценарий «reader + storage», а не сравнение фоновых очередей двух служб.
Сеть production, отказоустойчивый/Managed ClickHouse, повторный запуск с
checkpoint, остановка и неоднозначные INSERT здесь не измерялись.

## Вывод для настроек и следующих оптимизаций

При default и при включении исправленного/структурированного Data просадки
относительно апстрима на этом корпусе нет. JSON-разбор сам по себе добавляет
небольшую стоимость. Итог нельзя распространять на произвольный состав событий:
здесь сложные именованные блоки составляют около 3,5% записей.

Изолированные режимы указывают на большую стоимость проверки LGF перед каждым
событием. В коде оба дополнительных читателя проверяют длину и пытаются читать
EOF; сочетание strict и latest повторяет эту работу. Это первый кандидат для
отдельной оптимизации. Она должна сохранить обнаружение дописывания, усечения,
неполного хвоста и новых значений без изменения семантики курсора.

Полный контекст добавляет отдельную стоимость построения/экранирования JSON и
увеличивает Data. Его следует включать исходя из нужных данных, а не для самого
факта расширенного разбора. Настройки пользователя и production-код по результатам
этого замера автоматически не менялись.
